# JANSEE V4 全新云服务器部署清单

> 本清单是未来 V4 独立部署的唯一执行顺序。当前腾讯云服务器保留 Ubuntu 24.04.4 LTS，不重装、不格式化操作系统（无需格式化云服务器）；正式部署时先备份必要基础设施资料，不迁移 V2 数据库、文件、容器，再清理旧 V2 应用环境，最后全新部署 V4。本清单不表示任何清理或部署已经执行。

## 0. 已确定的部署原则

- [ ] **保留现有 Ubuntu 24.04.4 LTS 操作系统**，不格式化系统盘、不重装系统；除非未来发现系统本身不可用并另行获得明确授权，否则不改变这一决定。
- [ ] **V4 独立全新部署**：不迁移 V2 用户、积分、订单、作品、业务数据库、应用配置或运行目录；V4 使用自己的数据库、存储目录、环境变量和服务。
- [ ] **清理 V2 运行环境**：在备份和核对完成后，清理旧 V2 应用代码、容器/镜像/数据卷、数据库文件、旧服务进程与 systemd 服务、旧依赖目录、旧临时文件及不再使用的运行配置。
- [ ] **不要误删基础设施和 V4 必需资产**：保留并核验 SSH 管理通道、云安全组/防火墙、域名 DNS 管理能力、可复用的 TLS 证书及其私钥、云监控/救援能力。官方 BGM 曲库若仍是 V4 需要的资产，应先核验完整性后独立放入 V4 素材目录；不得把它当作 V2 运行垃圾删除。Whisper 模型如 V4 需要，可复用经过完整性核验的模型文件，但必须准备适配 Linux x86-64 的 whisper-cli，不能使用 Windows .exe。
- [ ] 不复用 V2 的 .env、支付密钥、数据库凭据、应用配置或 node_modules。V4 凭据应从对应服务的正式管理端单独取得/生成。
- [ ] 任何删除动作前都必须确认目标路径、备份结果和恢复方式；不得使用未经逐项核对的通配符或整盘删除命令。当前阶段不执行清理。
- [ ] 当前开发机工作区存在既有修改和未跟踪文件。发布时必须先审阅差异并形成明确的 V4 发布提交/制品，不得直接把整个开发工作区打包上传。
- [ ] 不把开发机的 .env、密钥、用户数据、storage、backups、Windows Whisper 二进制或浏览器配置带入发布包。

## 1. 部署前准备与清理顺序

1. 核实目标腾讯云实例 ID、公网 IPv4、系统盘/数据盘、磁盘挂载、CPU 架构、内存和剩余空间；确认当前系统仍为 Ubuntu 24.04.4 LTS。
2. 确认 SSH 登录、云厂商控制台/救援入口、云安全组和主机防火墙管理权限可用。**不得先删除当前 SSH 或网络入口。**
3. 盘点旧 V2 目录、Docker 容器/镜像/数据卷、数据库、systemd 服务、Nginx 站点配置、证书、定时任务、日志、BGM 和 Whisper 文件，形成明确清理清单。
4. 明确 V2 业务数据不迁移到 V4。按用户要求，用户、积分、订单、作品等 V2 业务数据不导入新 V4；但在执行删除前仍应按维护要求做必要的灾难恢复备份或快照，并确认备份存放位置及可读性。
5. 单独核验并保护继续需要的基础设施资料：SSH 凭据、域名解析控制权、TLS 证书/私钥（确认可复用且权限安全）、腾讯云安全组设置，以及 V4 所需的官方 BGM 曲库和 Whisper 模型文件。
6. 在维护窗口内停止 V2 服务；按已确认的清理清单移除 V2 应用、容器、数据卷、旧数据库和不再使用的服务配置。保留 Ubuntu、SSH 管理能力、网络配置及经核验需要复用的证书/素材。
7. 清理后复查系统服务、磁盘、端口、目录和网络状态，确认没有残留 V2 服务占用 V4 所需资源；不要为了“干净”而删除系统组件或未知目录。
8. 在独立目录（建议 `/srv/jansee-v4`）部署 V4，不依赖任何 V2 路径、进程、容器、数据库或配置。

## 2. 全新系统基线（在保留的 Ubuntu 上核验/补齐）

- [ ] 更新系统安全补丁、时区和时间同步；不重装操作系统。
- [ ] 创建独立部署用户，配置 SSH 公钥；禁用不必要的密码登录和 root 远程登录前，先验证新 SSH 会话可用，防止锁死远程管理。
- [ ] 安装或更新 Docker Engine 与 Docker Compose Plugin，并确认版本受支持。
- [ ] 安装或核验宿主机 Nginx、Certbot（或经审核的等效 TLS 入口）。
- [ ] 云安全组和主机防火墙只开放 SSH 管理端口、TCP/80、TCP/443；不得公网开放 8080、4100、5432。
- [ ] 确认 Docker 网段 `172.30.250.0/24` 不与服务器 LAN、VPN 或其他 Docker 网络冲突。
- [ ] 核验 CPU 架构、可用内存、磁盘容量、inode 和挂载点；为媒体、数据库、备份预留独立空间与告警阈值。

## 3. 域名与 HTTPS

- [ ] 将 `jansee.cn` 和 `admin.jansee.cn` 的 A 记录指向目标服务器公网 IPv4。
- [ ] 将 `www.jansee.cn` 配置为指向规范域名的别名（CNAME 或 DNS 服务商要求的等效记录）。
- [ ] 只有在服务器网络和 Nginx 均正确支持 IPv6 时才配置 AAAA。
- [ ] 核验现有 TLS 证书是否覆盖 `jansee.cn`、`admin.jansee.cn`、`www.jansee.cn` 且仍有效；不满足时重新申请证书。
- [ ] 安装 `deploy/nginx-host-jansee.conf.example` 对应的宿主机配置，确认真实证书路径正确后运行 `nginx -t` 并 reload。
- [ ] 验证 HTTP 强制跳转 HTTPS，www 跳转到 `https://jansee.cn` 且保留路径和查询参数。

## 4. V4 发布制品与环境变量

- [ ] 从已审阅的 V4 发布提交/制品部署到独立目录 `/srv/jansee-v4`；记录 Git commit 或制品 SHA。
- [ ] 依据 `deploy/.env.production.example` 在服务器创建全新的 `.env`，设置严格文件权限（例如仅部署用户可读写）。
- [ ] 设置唯一强随机 `POSTGRES_PASSWORD`；不可复用 V2 凭据。
- [ ] 设置实际管理员 `ADMIN_EMAILS`（或 `ADMIN_PHONES`），否则生产启动会拒绝启动。
- [ ] 设置 AI Director 的 HTTPS 地址、API Key、主模型和回退模型。
- [ ] 设置腾讯云 TTS Secret ID/Key；生产语音合成缺少凭据会阻止 API 启动。
- [ ] 设置阿里云短信真实凭据、签名和模板；生产禁止 mock/test 模式。
- [ ] 设置 OPCPAY API Key。Webhook Secret 是可选项；未配置时回调签名验证失败关闭，依赖已认证的周期性订单查询对账。若启用 webhook，必须填入服务商签发的真实密钥。
- [ ] 生成并安全备份 `PARTNER_PAYOUT_ENCRYPTION_KEY`（64 位十六进制）；该密钥必须跨重启和发布保持稳定，丢失会影响已保存的收款资料解密。
- [ ] 保持 `WEB_ORIGINS=https://jansee.cn,https://admin.jansee.cn`，`TRUST_PROXY_IP=172.30.250.2`，并确认 Compose 固定 IP 与之匹配。
- [ ] 生产配置中 `PAY_SIMULATE=0`、`JX_AUTH_TEST=0`；不得使用本地开发 Origin。

## 5. Linux 媒体运行依赖

- [ ] 在目标 Linux x86-64 架构上准备可执行的 Linux `whisper.cpp/bin/whisper-cli`；Windows `.exe` 不可用。
- [ ] 准备模型 `whisper.cpp/models/ggml-small.bin`，确认文件完整、可读；若复用原模型，先校验后复制到 V4 独立目录。
- [ ] 在服务器上运行 whisper-cli 的帮助/版本检查，并用受控测试音频完成一次 ASR 冒烟测试。
- [ ] 将经核验的官方 BGM 曲库放入 V4 独立的 `materials/` 目录，核对文件数量、大小和抽样可读性；不依赖 V2 运行目录。
- [ ] 确认 `materials/` 目录完整，容器内 `/app/materials` 可读。
- [ ] 创建 `storage/v4` 并授予容器运行用户所需的最小写权限；确认重启后挂载仍存在。
- [ ] 确认媒体存储剩余空间告警、TTL 清理和备份策略已配置。

## 6. 配置检查与启动

在 V4 仓库根目录：

```bash
docker compose -f deploy/docker-compose.v4.yml config --quiet
docker compose -f deploy/docker-compose.v4.yml build
docker compose -f deploy/docker-compose.v4.yml up -d
docker compose -f deploy/docker-compose.v4.yml ps
docker compose -f deploy/docker-compose.v4.yml logs --tail=200 api
```

注意：完整 `docker compose config` 可能展开环境变量；不要把包含密钥的输出贴到工单、聊天或公开日志。优先使用 `--quiet` 做语法/配置校验。

- [ ] PostgreSQL 健康，API 等待数据库健康后启动。
- [ ] 检查 API 启动日志中的 migration 清单，确认迁移成功且无失败。
- [ ] API 健康检查通过；Web 容器健康检查通过。
- [ ] 宿主机 Nginx 配置测试通过，两个正式域名可访问。
- [ ] 公网无法连接 TCP/8080、TCP/4100、TCP/5432。

## 7. 真实业务验收

- [ ] 官网与后台分别通过 HTTPS 打开；后台 Host 路由正确。
- [ ] 注册、短信验证、登录、退出、会话过期行为正常。
- [ ] 管理员身份白名单生效，普通用户不能访问管理接口。
- [ ] 上传图片/视频，素材落盘且容器重启后仍可读取。
- [ ] 完成一次真实 AI 导演调用、腾讯 TTS 配音、视频渲染、作品下载。
- [ ] 验证口播/切片依赖的 Linux Whisper ASR 实际可执行。
- [ ] 完成 OPCPAY 真实支付、支付状态查询/对账、退款相关验收；禁止用模拟支付结果代替。
- [ ] 验证积分、签到、推广、合伙人、提现、站内信等关键业务流程。
- [ ] 验证作品过期清理后，前台作品列表同步移除失效记录。
- [ ] 检查 Cookie 的 Secure、HttpOnly、SameSite 属性及跨域行为。

## 8. 备份、恢复和交付

- [ ] 配置每日 PostgreSQL 备份，并把备份同步到独立机器或对象存储；同机备份不算灾备。
- [ ] 对 `storage/v4` 媒体文件制定独立备份策略；数据库 dump 不包含媒体文件。
- [ ] 至少完成一次 PostgreSQL 恢复演练和一次媒体文件恢复演练。
- [ ] 验证备份加密、访问权限、保留周期和告警。
- [ ] 记录发布 commit、镜像摘要、数据库迁移版本、环境变量清单（只记变量名，不记录值）、域名证书到期时间和回滚制品。
- [ ] 完成验收签字后才对外切换正式流量。
