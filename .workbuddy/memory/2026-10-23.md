## 路线级决策：生图优先（Image-First）

用户提出把「AI 生视频」改为「AI 生一篇精美场景图 + 程序贴用户商品图」，问是否对 CPU/内存/FFmpeg 更友好。

**实测（1080×1920 · 30fps · 8s · 240 帧 · crf18 medium，同机）**

| 环节 | 墙钟 | 峰值内存 |
|---|---|---|
| A 视频背景 + 逐帧 overlay | 27–40s | 678MB |
| B 图片背景 + 一次合成 + 推近出片 | 8.2s | 590MB |
| C 只出静态图（sharp） | 0.36s | ~60MB |

- 时间省 70%，吞吐 1050 → 3600 单/小时
- **内存只降 13%**：ffmpeg 内存大头是 x264 编码器缓冲，不是解码输入。只要还出 8s 视频，这块躲不掉
- 素材体积 5.5MB → 256KB（21 倍）

**必须纠正的理解**：不能让 AI 把用户图"画"进屏里（logo 变形、颜色被重绘）。AI 只生空屏场景，程序贴图。延续铁律「几何由程序保证，不由模型保证」。

**真正的商业价值不在 CPU，在资产化**：场景图可复用（20 张模板跑 1 万商品，边际成本趋近 0），视频是一次性消耗（20 段跑 20 单就没了）。

**产出**
- `docs/visual-gallery/image-first-pipeline.md` — 完整评估（数据/三个技术点/落地顺序）
- `storage/tmp/bench/bench.mjs`、`bench2.mjs` — 可复现基准
- `storage/tmp/demo-img/build.mjs` → `demo-image-first.mp4` — 最小可运行 demo（静态场景图 + 商品轮播 + 整幅推近 1.045×，8s/30fps/1080×1920/2.16MB），验证「静图也能出有动感的片」且几何不漂移

**关键手法**：整幅推近 = 摄影机推近，屏和屏内容一起放大。屏内容在推近**之前**就贴死，所以几何永远对齐。反过来（先推近再贴屏）会漂移。

**风险**：静图做动效容易"死"。首选解是「屏内商品轮播」——画面里唯一合理该动的东西，且正是 v4 引擎已有能力。

**下一步**：第一批先锁死"屏必须是矩形平屏"跳过 perspective；生 3–5 张场景图人工标四角存模板 JSON；用 v4 引擎跑通轮播出片。

## 补充：静止版 vs 推近版 实测（01:10）

`storage/tmp/demo-img/build.mjs` 已支持 `PUSH=0/1`（是否整幅推近）与 `DUR` 环境变量，PER 按 `(DUR+(N-1)*XFADE)/N` 自动算，总时长正好等于 DUR。

| 版本 | 处理耗时 | 码率 | 体积 |
|---|---|---|---|
| 静止（只有屏内轮播） | 10.4s | 4525kbps | 4.32MB |
| 推近（屏内轮播 + 1.045×） | 13.1s | 11659kbps | 11.12MB |

- 推近多花 2.7s（+26%），换"不像一张图"
- 静止版码率天然低，因为画面真没变化；对静态内容 4.5Mbps 足够，但仍建议走推近版
- **重要约束**：8s 时长下，3 张 = 2.9s/张（舒服），9 张 = 1.2s/张（看不清）。要么延长到 15s，要么只取 4–5 张。上限不是"最多 9 张"这条铁律，是"8 秒里人眼能看清几张"

**码率口径修正**：不要笼统说"抖音必须 ≥12Mbps"。12Mbps 是针对有运动/噪点的内容；静态画面 4.5Mbps 视觉上等价。真正会被压烂的是 A 方案那种 186kbps。

## 补充：张数与时长（01:16）

用户明确：**不设固定 8 秒，时长由上传张数决定（上限 9 张），最长可达 1 分钟。**
`build.mjs` 已支持 `N` / `SEC_PER` / `DUR` 环境变量，输出文件名带张数与时长。

| 张数 | 时长 | 处理耗时 | 体积 |
|---|---|---|---|
| 3 | 8.0s | 13.1s | 11.12MB |
| 6 | 16.3s | 44.2s | 21.55MB |

**踩到坑：耗时超线性。** 时长 2.04 倍，耗时 3.37 倍。原因是轮播用 `xfade` **链式**叠加，第 N 次 xfade 要重算前面全部帧，复杂度 O(N²)。
9 张约 24s 片 → 估算 85–100s 处理；1 分钟片 → 200s+，8 核并行约 26s/单，开始疼。
改法（暂不做）：并行 overlay + 每层 alpha 淡入淡出，成本 O(N)。代价是两张半透明叠加时会轻微透出屏底。**现阶段 9 张 85s 能忍，不提前优化。**

**内容判断**：9 张摊到 60 秒 = 每张 6.7s，第 3 秒就空了。1 分钟要用满必须有结构（多场景切换 / 每张配卖点文案 / 同一商品三个景别），这三样项目里目前一个都没有。
**推荐**：时长自动 = 张数 × 3 秒（9 张 = 24s），不给用户时长滑杆。1 分钟留作硬上限，等多场景能力上线再放开。

## 「PPT 感」的根因（01:38）

用户指出：程序画的屏 PPT 感太强，AI 生的场景图一体感更好。判断正确。

**根子不在"屏是程序画的"，在"光和影是程序造的"。** 程序永远伪造不好的五件事：
1. 环境染色（树叶的绿、天空的蓝染到屏框上）
2. 边框落影（阴影形状取决于光源角度，画错一眼假）
3. 玻璃反射（屏面对街景象的映照）
4. 前景遮挡（树枝、行人压在屏前）
5. 材质瑕疵（灰尘、划痕、边框接缝）

五条逐条手调成本极高且易露馅，AI 一张图全给。

**关键推论：一体感来自光和影，不来自"屏是斜的"。** 一个正对镜头的户外屏，照样可以有环境染色、边框落影、前景遮挡。所以第一批仍可锁「平屏、正对镜头」，省掉 perspective 校正，同时拿回一体感。

**一条必须写进生图提示词的硬约束：屏面内不能有任何遮挡。** 否则贴商品图时会把遮挡一起盖掉，反而更假。遮挡只能发生在屏框外。

## 22:0x 屏内留白：黑底淘汰，定「边缘像素延展 + 提亮」

用户："不用加黑色底色，本来屏上就设计的有色彩。" 跑了 5 版对比（`storage/tmp/scene-test/fuse2/3/4/5.mjs`）：

| 版本 | 做法 | 结果 |
|---|---|---|
| 黑底（原） | 上下带纯暗渐变 #0a0b0e→#1b1e26 | 像"只亮了一块"的印刷品，屏没有整片发光 |
| 平均色底 | 取上下边缘**平均色**做渐变 | **脏**。橄榄灰，且是"外来色块"，与画面无关 |
| 主色带 | 色相直方图取峰值做品牌色块 | **更差**。深棕/橄榄，"像装裱在木框里"，像画框不像屏 |
| 边缘延展·压暗 | 顶/底行纵向拉伸、左/右列横向拉伸，brightness 0.52 + 外侧暗 0.55→0.08 | 颜色自然了，但带子比画面暗太多 → "图片浮在暗盒上" |
| **边缘延展·提亮（定案）** | 同上，brightness **0.78** + 外侧暗 **0.30→0**，blur ≤4 | 整块屏成一整片发光面，接缝几乎看不出 |

**结论：留白区的颜色必须来自画面边缘的像素本身（列/行延展），且亮度要接近画面（0.78），不能压暗。** 压暗会让屏"变成盒子"，平均色/主色会让屏"变成画框"。

**4:3 是唯一还会露馅的比例**（上下各 136px、差 272px，是屏高的 30%），延展能缓解不能消除；3:4（左右各 78px）和 1:1（上下各 33px）延展后基本无缝。

几何：场景图量到屏 960×1038、裁切归一化后 820×887 @(130,421)（屏中心仍压 45% 线）。

### 追加：用户提"不取色直接贴"，实测发现场景图的屏自带彩色底

`storage/tmp/scene-test/fuse6.mjs` 三种做法（4:3 / 1:1 / 3:4 各一张）：

| 做法 | 结果 |
|---|---|
| ① 直接贴（留白 = 场景屏原样像素） | **意外地好**。Gemini 这张场景图的屏里画了紫蓝渐变 + 光斑，直贴后留白露出那块彩色，正好满足"屏上有色彩"。但紫底偏亮、与商品硬碰 |
| **② 直接贴 + 只压留白区（0.34 黑，evenodd 挖洞，商品区不压）** | **最优**。背景退后、商品前跳，接缝被压弱 |
| ③ 边缘延展 | 最贴商品色，最柔和，但属"程序造的色" |

**关键发现：留白的处理可以前移到生图阶段。** 只要提示词要求"屏面显示淡雅的品牌渐变背景"，每张场景图自带可用底色，合成时直贴即可——比程序延展更真（颜色与环境光天然一致），且零成本。

**接缝不必消除**：真实屏播放内容时，内容块与背景本来就有边界；硬边是"这是块屏"的证据，不是缺陷。

## 12:0x 海报路线打样：一套设计语言 + 三分支参数（定案）

用户转向："生视频不稳定，直接生成设计海报，商品图放海报里。" 做了 4:3 / 1:1 / 3:4 三张（2:3 弃用）。脚本 `storage/tmp/poster/build.mjs`。

**核心结论：一套版式不可能三比例通吃。** 图高 4:3=810、1:1=1020、3:4=1173，差 363px，标题位置无法固定。正确形态是**一套设计语言（配色/字体/元素/间距规则共享）+ 三组落位参数**。

| 比例 | 商品尺寸 | 占宽 | 对比屏方案（820×615 / 820×820 / 675×900） |
|---|---|---|---|
| 4:3 | 1080×810 | 100% 满宽 | 短边 +32% |
| 1:1 | 1020×1020 | 94% | +24% |
| 3:4 | 880×1173 | 81%（压图） | +30% |

**三条硬规则（踩坑换来）：**
1. **底色必须跟商品图走**。白底商品图配深色底 = 一张白纸贴在黑板上，一眼假；改米白底后立刻成立。实现为 `LIGHT` 分支：亮暗两套背景/文字/强调色，浅色时关掉溢光与暗角、噪点降到 0.016。
2. **商品图的溢光必须做径向羽化**（`dest-in` + radialGradient）。不做的话，在深色背景上会露出一个比图片大的亮矩形，读作"照片贴在一个发光方块上"。
3. **图底渐变压暗不能超过图片高度的 45%**。超过就形成"雾带"，浅色图片上像脏了（白桌布渐到深青 = 一眼假）。3:4 的压图渐变只覆盖底部约 273px。

**版面结构**：品牌行(JANSEE + 序号 + 1px 线) → 商品图 → accent 短线 → 中文标题(80px XW 宋体, 字距16) → 英文副标(22px, accent 色, 字距14) → note(20px 灰) → 底部 200px 超大英文单词(2.6% 白 / 4.2% 黑，被抖音文案区盖掉也不心疼)。

**纪律**：内容全部收在 y ≤ 1470（抖音底部文案区），三张实际内容底 1398 / 1468 / 1420。

**已知局限**：本版是极简 4 行字，无卖点列表/价格/CTA；加这些会破坏版面，属于另一种产品形态（促销海报）。动画（整幅推近 1.045、文字入场）尚未接。

## 多商品海报：翻页形态定案（只换内容块，背景不动）

用户问"海报是整页换还是只换商品图，哪种效果好"。

**结论：换"内容块"（商品图 + 文字块），背景渐变/大字/噪点全程不动，0.35s 交叉淡化。**

三条理由：
1. **文案跟商品绑定**。若只换图、文字不动，就会出现"标题写晨间现烤、画面是蛋糕"的图文不符；若文字也换而背景也换，整屏闪色 = 廉价。
2. **背景跳色是最容易露怯的一环**。多页各自按商品主色派生背景，切页时整屏色相跳变，读起来是"PPT 换页"；背景固定则读起来是"同一块版面在翻内容"。
3. **分层架构天然支持**。`storage/tmp/poster/layers.mjs` 已把 base/brand/title/sub/note/prod/sweep 拆开，换页只需 prod+text 三层各备 N 份，base 一份复用，成本几乎为线性，不是平方级（对比 ffmpeg xfade 串联链）。

**硬约束：同一片子内所有页必须同比例。** 比例不同则图片块高度不同、文字块位置必须跟着挪，切页会"跳"。混合比例时退回"整页切换 + 每页各自排版"（此时背景允许换，但要求同色系）。

**"只换图"唯一成立的场景**：文案是品牌级的（店名 + 口号 + 地址/电话），不写具体卖点。那更像电子菜单/灯箱，观众读作"一个广告位在播图"，而不是"一套设计"。用户主打商品卖点，不适用。

工程口径：`-loop 1 -i png` 每帧重复解码 1080×1920 PNG，7 层 × 240 帧 = 58s；改 `loop=loop=N:size=1` 在滤镜内复制后约 10s。这条已写进 `animate.mjs` 头注释。

## 定位判断：短视频赛道的真威胁不是同行多，是平台免费送

用户明确"简兮只做短视频赛道"。前一轮已确认：抖店「AI 生成图文」免费、剪映 DreamPoster 免费、淘宝星辰图生视频免费。→ **"更好的出片工具"这条路径在结构上关闭了**，因为它卖的东西平台正在免费发。

**商家的三个真问题是分层的：**
| 问题 | 谁能解决 | 现状 |
|---|---|---|
| 没审美（不会排版） | 模板方（稿定/剪映） | 已饱和，年费 159 |
| 没时间（不想学、不想做） | 服务方（代产出） | 有市场，但人力生意，规模不经济 |
| **没素材（没有能发的画面）** | **没人解决** | 工具方默认"你有素材"，而这恰恰是最大缺口 |

**建议定位：从"出片工具"改成"素材工厂"——卖"你没有的画面"，不是"你不会的剪辑"。** 一个餐厅老板有 9 张菜品图，没有一条能发的片子；这不是工具能解决的，是供给侧缺口。
**风险**：若只做"好看的轮播海报"，仍停留在"没审美"这一层，与稿定正面撞价。必须往画面形态的多样性上靠（同一张图出多个场景/景别/运镜），产出"可发的内容量"。
**待验证**：找 3 个真实商家问"你现在手上有几条能发的视频、为什么不发"，答案决定方向，比继续做模板便宜。

## 客群纠正（用户明确）：线上商家 + 线下商家的短视频推广，个人创作者非主力

我上一轮把方向引到"商家没素材"，用户纠正了目标客群。修正后的判断：

**两波人的图源质量不一样，这决定产品适配度不同 —— 这是硬约束，不是偏好。**
| | 线上商家（电商） | 线下商家（本地生活） |
|---|---|---|
| 图源 | 白底图/场景图是生产资料，必须拍好 | 多数只有手机随手拍，质参差 |
| 素材的财务属性 | 流量杠杆（主图视频直接影响转化，可 A/B） | 成本项（钱在投放和探店达人） |
| 需求节奏 | 多 SKU 批量上新 | 高频但低预算 |
| 现有解 | 淘宝 5–20 元/条 代做、平台免费工具 | 本地代运营 3000–8000/月、达人置换 |
| 能否算 ROI | 能 | 只能靠团购核销间接算 |

**结论：线上优先。** 理由是产品前提成立（图能看）且 ROI 可归因；线下要先解决"输入图质差"，否则同一条链路的产出会明显更差。

**关键认知：这两波人的现有解不是软件，是人（外包/代运营/达人）。** 所以对手盘不是剪映，是"淘宝 5 元/条"和"本地代运营 3000/月"。简兮要赢的姿势是"比外包快、比代运营便宜、比达人可控"，不是"比剪映好用"。

**定价纪律：按条/包月，不做工具订阅。** 这波人不买软件，只为结果付钱。
**最大风险：中间地带。** 要么技术把成本压到 1 元/条（量取胜），要么服务卖到连锁高客单（质取胜）；卡在中间最危险。
**个人创作者不做主力是对的**：他们要风格不要模板，时间多愿自己剪，付费能力最低。

## 13:1x 定位纠正（用户明确）：简兮是平台，图片成片只是其中一个版块

完整版块：**图片成片 / 视频配音 / 切片 / 分镜成片 / 口播视频**。前几轮把"图片成片"当整个产品评估，格局错了，需修正。

**平台的真价值不是"版块多"，是「统一素材层 + 一次输入多形态派生」。**
- 若各版块各要一套输入、各操作一遍 → 只是几个工具拼在一起，不比单点工具强。
- 若一次上传（商品图 + 卖点 + 价格 + 人群）→ 派生 5 种形态 → 单点工具做不到，这才是平台壁垒。
- **技术前提：先有统一素材数据结构（商品档案），各版块从它派生。** 没有这一层，多版块就是伪平台。这是平台化第一优先级，比做第 2 个版块更重要。

**图片成片在平台里的角色 = 入口版块，不是利润版块。**
理由：它是唯一"零成本输入"的版块（传图就出），获客门槛最低。评判它的标准因此改变——不再看"能否赢稿定"，而是看**首次试用的成功率**（传图就成功、不报错、不丑），因为这决定用户愿不愿意试第二个版块。利润应该来自口播/分镜/切片（价值高、门槛高）。

**这加强而非削弱"卖给服务商"的判断**：服务商最痛的是要给客户凑齐一整套内容（图 + 口播 + 切片），现在要用 5 个工具、5 次操作。平台一次给全套，这个痛点比"批量"更硬。

**平台化的风险**：五个版块都只是平庸，等于没有招牌。必须有**一个版块足够强当招牌**（建议就是口播或分镜，因为价值高、竞品弱），其余够用即可。不能五个都在 60 分。

## 13:2x 平台交互铁律（用户定义，全平台统一）：三步成片

**1 丢素材 → 2 写描述 → 3 成片。** 五个版块共用同一套心智模型。

**修正我上一轮的错**：我说"删掉文案输入框"，是把两件事混了——
- **文案** = 直接出现在画面上的字（用户写不好，会写出"本店新品上市欢迎选购"）
- **描述** = 告诉 AI 这是什么商品、卖给谁、凭什么买（用户一定会写，因为他最懂自己的货）
→ 正确做法：**描述必须留，画面文案由程序从描述生成。** 用户说意图，不说字。

**三步模型的真正价值：把"操作"统一成"表达"。** 传统工具是点按钮（选模板/拖时间轴/调参数），三步是说话。输入变简单，能力变复杂。

**护城河从"版面"移到"描述"。** 6488 个模板是死的，描述是活的——它含品类/人群/卖点/场景/价格带/禁忌，这些是模板方永远拿不到的。**同一个版面 + 不同描述 = 不同的片子**，同质化风险被描述化解。这条推翻了我之前"海报风格是红海、没有壁垒"的部分悲观结论。

**架构判断：差异收在第 1 步，统一做大在第 2、3 步。**
- 第 1 步（丢素材）各版块不同：图片成片=图、视频配音=视频、切片=长视频、分镜=图、口播=图+形象
- 第 2 步（写描述）、第 3 步（成片）全平台共用 → **一次描述，五个版块都能用**
- 所以底层应该有统一的「描述解析层」+ 统一的「成片输出层」，版块差异只在素材接入层

**唯一风险点：第 2 步是三步里唯一需要用户"想"的一步**（另两步都是动手）。商家常写不出（"我不知道怎么形容我的面包"）。→ 必须做成"选 + 改"而不是"从零写"：引导式短问题（卖什么/卖给谁/凭什么买）+ 示例描述 + 从商品页一键导入。目标 30 秒内写完，否则第 2 步就是流失点。

## 13:2x 第 2 步形态定案（用户定义）：少量关键词 → LLM 写 → 配音/字幕/BGM 一起成片

用户输入不是问答、不是长描述，**只是少量"想突出的东西"**（关键词级），LLM 负责展开成完整文案，然后配音 + 字幕 + BGM 一并产出。

**结构价值：一份文案，三处消费。** LLM 写出的文案同时变成 ①画面文字 ②配音脚本 ③字幕。所以 **LLM 这一步是"一票否决"位置**——文案定了，画面字、配音、字幕全定。→ **核心资产是「描述→文案」这段 prompt 与语料，比版面重要得多。** 这也把上一轮"护城河在描述"精确到位：护城河在转换环节，不在描述本身，也不在版面。

**最大风险：配音不是附加值，是木桶最短板。**
反直觉判断：**无声的片子，观众读作"品牌海报"；机器音解说，观众读作"AI 批量生成"，后者更廉价。** 所以配音要么做好（选音色/控语速 4.2–4.6 字每秒/轻微情绪/句间留 0.15–0.25s），要么不做，中间状态最伤。图片成片加配音是"图文轮播→有解说"的实质升级（能承载图片承不下的卖点、提升完播），但必须一次做对。

**三个工程红线（易漏）：**
1. **字幕必须与配音逐句对齐**，错位即废；字体位置按抖音习惯（中下部、白字黑边）。
2. **BGM 版权**——没授权会被抖音静音或降权；音量压到 -18dB 左右，不能盖住配音。
3. **BGM 情绪要与文案一致**，餐饮轻快、建材稳重，程序按品类选，不给用户选。

**第 2 步该问什么：能推断的不要问。**
- 必问（1 项）："想突出什么"——自由输入，关键词即可（"低糖""现烤""上班族早餐"）
- 自动推断：品类（看图）、明暗（看图，决定版面明暗分支）、风格倾向
- 兜底可改：人群（推断不出时给默认值 + 让他改）
→ 品类/人群若拿不到，LLM 写的文案必然泛（餐饮和建材的说话方式完全不同）。

**建议加一个低成本高回报的交互**：LLM 写完文案后**先给用户听一句配音（10 秒）**再出全片，不满意当场换。这比出完整片再重来便宜一个量级，也是"哇"的第二个时刻（他写三个词，变成一段有解说的片子）。

## 13:29 承载物方案怎么落地：底板预制 + 程序透视贴图（不是 AI 现场生成）

用户质疑："用户只上传一张图，怎么让它出现在快递箱/杂志/灯箱里？"

**答案：承载物场景是预制的资产，每个场景里预留一块「承载面」，用户的图按那块面做透视映射贴上去。** 跟之前"街景广告屏"完全同一套方法，只是容器从"屏"换成"箱内的纸 / 杂志右页 / 灯箱面板"。

**每个场景模板要存三样：**
1. 场景底图（快递箱的箱体、盖子、泡沫粒、光向）
2. 承载面四角坐标（可以是梯形，支持透视）
3. 材质叠加层（纸纹 / 箱内阴影 / 反光 / 边缘投影）

**素材来源三种，可靠性排序：**
| 来源 | 可靠性 | 成本 |
|---|---|---|
| **拍真实照片 + 把承载面抹成纯色/留白** | **最可靠**，光影天然真实 | 一个场景 10 分钟，一次性 |
| 程序渲染（画箱子/杂志的形） | 中，光影要手调 | 低，但容易"PPT 感" |
| AI 生图要求"预留空白区" | **低**，已验证：模型不会精确留白，四版实测屏全小于规格 | 低但不可控 |

→ 推荐：**拍摄 + 抹白 + 标四角**，10 分钟一个场景，之后跑一万单。

**关键：为什么这个能成，而之前的户外屏不成？**
不是因为技术变了，是因为**内容合理性**变了。
- 户外 LED 屏放的是动态广告，塞一张满幅白底产品照 → 过曝 1.68×、形态不对 → 一眼假
- 快递箱里/杂志页上放一张印刷彩页 → **本来就该是一张平面图** → 白底彩色图完全合理
→ **换容器换掉的是"内容真不真"这个问题，不只是换背景。** 这条是整个方案成立的根基。

**成本结构**：场景一次性制作 → 无限复用。12 个承载物 = 12 个资产 = 一个商品能出 12 条不同的片子。这是"内容量"的来源。

## 13:31 澄清：承载物方案的三个岔路（用户理解基本正确，但"生视频"要分清）

用户复述："提前生一段视频，里面是快递箱/杂志/灯箱/老电视，我们把图放进这些场景，替代之前放进屏里。"

**动作本身完全正确。但要拆三个岔路：**

**岔路一：场景是「预制素材」还是「AI 现场生成」？**
- **模板必须用预制素材**（拍摄 / 渲染的静态图或短视频）。理由：模板要固定、要可复用一万单；AI 每次生成都不同，无法做模板。
- AI 生视频只适合"一次性特效"，不进模板库。
- **这条是硬边界**，否则又回到"每次出片结果不一样"的老坑。

**岔路二：就算用 AI 生视频，判据也要改。**
之前"尺寸约束失败"的根因是**要求模型精确执行像素坐标**（四版实测屏全小于规格）。如果改成"不要求精确坐标，只要求承载面够大、够正、够清晰，位置我们自己量"，成功率会高很多。但即使这样，每次结果不同 → 仍不能做模板。**结论：测量路线可以做特效，做不了产品。**

**岔路三：场景是「图」还是「视频」？**
- 静态图 + 程序推近 = 能出片，成本最低，第一批用它
- 预拍短视频（开箱动作、光扫过）= 动感更好，但素材成本高一个量级，第二批再上

## 承载物相对户外屏最大的结构性优势（之前被忽略）

**承载面的形状可以由我们设计，不再受"物理屏"约束。**
- 户外屏：屏是物理物件，比例固定 0.911 → 四种商品比例必有一种要留白 → 为此折腾了一整天的 letterbox / 边缘延展 / 黑边压暗
- 承载物：箱内那张纸 / 杂志页 / 灯箱面板，**可以按商品比例裁成 4:3、3:4、1:1 任意形状** → **留白问题从根上消失**

→ 这一条比"有叙事""有信用背书"更实在：它把整个产品最难的技术债（比例不匹配）直接删掉了。商品图可以 100% 铺满承载面，永不裁切、永不 letterbox。

| 文件 | 职责 |
|---|---|

| `compose.mjs` | 单应变换贴图 + shading transfer + 遮挡保留 + 底板预处理 |
| `page.mjs` | 生成"印在纸上的那一页"（按承载面比例，不是 9:16） |
| `video.mjs` / `stitch.mjs` | 8s 推近出片 / 三联对比 |

**四个坑（都踩过，已修）：**
1. **2:3 场景图不能直接 resize 到 9:16**——1024×1536 拉成 1080×1920 会横向拉伸，而四角只按宽度换算，导致贴图整体偏移、只覆盖半张纸。必须先按目标比例裁切再等比缩放。
2. **检测用"亮度"不可靠，要用"通道极差"**：白纸不管多暗都是中性色（通道差 ≤10），牛皮纸/泡沫/木箱都带暖色（≥30）。用饱和度主判据能把阴影里的纸也收进来。
3. **四角不能取连通域极值点**：边缘被阴影吃掉时会内缩。改成"每行左右边界 + 每列上下边界分别拟合直线，四线求交点"，局部边缘缺失也能还原完整四边形。
4. **生成图右下角有"AI生成/WORKBUDD"角标**：修补（用上方纹理覆盖）不可靠，直接裁掉底部 66px 最简单。

**实测数据（1080×1920 画布）：**
- 底板 1024×1536 → 裁底 66 → 按 9:16 裁宽到 830 → 缩放 1.30×
- 承载面 667×593（原图）→ **871×775（画布），占画布 32.6%**
- 1:1 商品内缩后约 780×775 → 面积占画布 **29.4%**
- 对比海报（poster-1x1.jpg）：商品 1020×1020 占画布 **50.2%** → **承载物的商品面积只有海报的 58%**

**必须修正的一个说法：承载面形状不由我们决定。** 上一轮我说"箱内那张纸想什么比例就什么比例"——那是对"自己拍底板"成立；用 AI 生图时，纸的比例是模型画的（这张 1.124），所以**一张底板只能服务接近这个比例的商品图**（1:1、4:3 可以，3:4 会左右露白）。要覆盖全比例，得让生图出"接近方"的纸、或做多张不同比例的底板。

**判断：承载物技术上成立（透视、光影、遮挡都对，箱子质感真实），但商品占比是硬伤（29% vs 海报 50%）。** 它的价值不在"更好看"，在"一个商品出 N 条完全不同的片子"——这是海报做不到的内容量。建议定位为第二形态而非主形态。
**成本**：一张底板一次生图（5–10 credits）+ 一次人工核四角（约 10 秒）+ 合成 10 秒/张；8s 推近视频渲染 16 秒、3.5MB。

## 14:0x 用户提问「只能白底或纯色底才能做吧」→ 版式必须拆两套

用户这个质疑是对的，但结论不是"只能白底"，是**判断依据放错了**：真分界线不是"底白不白"，是"**图里有没有场景信息**"。

**两条硬几何（新推出，可复用）：**
- 面板版商品占画布 = 面板占比 × 原图内商品占比。例：原图商品占 40%，4:3 面板 42.2% → 实际只有 **16.9%**。
- 全出血版商品占画布 = 裁切后原图内商品占比（图铺满、无边）。**注意 上一轮写成"全出血永远 ≥ 面板版"是错的，漏算了裁切**：铺满 9:16 必须等比裁掉宽度，裁切量随图源比例暴涨——**4:3 横图裁 58%、1:1 裁 44%、3:4 只裁 25%**（= 1 − 0.5625/比例）。4:3 裁掉 58% 宽，商品大概率被切断，后面这个优势就不成立了。**正确口径：只有竖图（≥3:4）的全出血商品占比才稳定高于面板版。**

**"出血"是什么**：印刷术语，指画面故意超出裁切线，裁完边缘不留白边。搬到视频里 = **图铺到画布四边、零留白**。面板版与全出血的唯一区别就一句：**面板版的图有边界（是版面里的一块），全出血的图没有边界（图就是版面）**。

**全出血三道工序（不是"直接把字压原图上"）**：①等比裁切到 9:16（不拉伸，但**必须裁**，与"不裁切不拉伸"铁律直接冲突，这是全出血的真实代价）②铺满 1080×1920 ③底部压暗渐变（从图高 45% 起，不超过）④文字落在压暗区，标题提到 96–110px。

**分流三档（修正版）**：①白底/纯色底 → 面板版（零加工，最干净）；②竖构图实景图（比例 ≥3:4）→ 全出血版；③横构图实景图（4:3）→ 仍走面板版（全出血要裁 58%，商品会被切）；④背景杂乱且主体 < 40% → 拒收。

**一个顺手的巧合**：线下商家用手机拍的图**基本都是竖的**（手机默认竖持），天然落在 3:4 甚至更竖——所以全出血恰好吃的是线下商家这个客群，裁切量 15–25%，可接受。横图几乎只出现在线上商家的电商详情图里，那些本来就走面板版。两套版式跟两类客群几乎一一对应。

**抠图为什么不做**：理由从"技术上会出错"升级为"**业务上不需要**"。线下商家的图是门店/菜品/环境，抠出来反而丢掉唯一卖点（场景），抠图对它们等于毁图；线上商家的主图被电商平台规则强制白底，本来就不需要抠。两头都不需要，这条技术就永远不该做。

**客群对应**：线上商家主图（平台强制白底）→ 面板版；线下商家（全员实拍）→ 全出血版。用户客群含线下商家，所以两套不是可选项。

**纠正一条旧数**：记忆里的"8.2s/条"是早期极简 demo，不是 7 层版。7 层的面板版今天实测 20.2s。**两套版式成本基本持平，全出血不更贵**——之前拿 8.2s 当基准的所有推理都要重算。

**四条工程结论（都踩过）**
1. **逐帧缩放是唯一真瓶颈**：zoompan 和 `scale=eval=frame` 一样慢，8 秒多花 7s。`crop` 逐帧平移只多花 3.3s。全出血改用**慢速漂移**（1188×2112 出图，8 秒内左上各移 ≤140px）代替推近——实景图本来就不需要推近，它已经是照片了。
2. **文字不动、只动图**。面板版是整幅推近（图文同平面，读作摄影机推近）；全出血的文字是叠加层，跟着放大会读作"模板被缩放"。所以 zoom 只能作用于照片流，文字层原样叠加。
3. **压暗必须按底区亮度自适应**，固定参数在亮图（白托盘 mean≈0.58）上失效、在暗图上压成死黑。`maxOp = 1 - 0.22/mean`，clamp [0.70, 0.95]。更要紧的是**压暗必须在标题基线之前就走到满值**：0.36 不透明度压在灰底上，白字只有 2.3:1 对比度，不可读——第一版就翻在这。
4. **噪点层不能在透明画布上用 overlay 混合**：backdrop alpha=0 时 overlay 返回源色，会变成一整层不透明灰，把下面所有层盖掉（第一版全屏灰就是这个）。实景图本身有颗粒，全出血**直接不加噪点**——加了还把体积从 2.3MB 推到 13.6MB（运动的颗粒压不动）。

**版面定案（全出血 / 3:4 图源）**：压暗 1240→1400 走满；文字栏 y=1318、标题 96px@1416、副标 22px@1456（≤1470 安全线）；顶部 0→420 压 0.70 给品牌行读得出来；accent 从图主色派生（本例 #e47b58）。

## 14:5x 用户回溯最初方案（转场+叠化）→ 定位修正

### 一、最要紧的一条发现：sharp 的 SVG 渲染器根本不认 font-family

实测 21 个字体家族名（SimSun / KaiTi / 微软雅黑 / Palatino / Georgia / 项目自带站酷系列 / XW），**渲染结果逐像素完全相同**，全部 fallback 到同一个兜底字体。

## 16:2x 阶段性判断：技术可行性过了，产品链路没过

用户问"整个流程基本就通过了？"。核查后分两层回答。

**已闭环**：三洞位 × 五套版式（15 组几何校验 0 问题）、洞位自动选择、V4 可搭配预览、成片成本 4.7–8.9s / 0.20–0.21MB。

**三个真缺口（按严重度）**

1. **预览与成片是两套渲染引擎，必然不一致（最要紧）**。V4 预览走浏览器 `<text>` + `font-family`（依赖系统字体匹配，实测 lyT 用的就是 text，`<path>` 全文仅 4 处）；Node 出片走 `opentype.js` 字形转 path（精确轮廓）。字号、字距、字重、baseline 都会有偏差，且浏览器字体匹配失败是**静默回退**（已踩过等线 Light 那次）。后果：拿 V4 当验收工具会得出"预览好看、成片翻车"的假结论。**必须早决**：要么 V4 改成展示服务端渲出的真实 frame，要么明确 V4 只用于看结构/比例、不作为质量验收依据。
2. **白底电商图零实测**。`storage/uploads` 全部是实景图（最亮的 bakery 0.748、coffee 0.631，都非纯白底）。线上商家主图按平台规则强制白底，是量最大的一半客群，而"白底矩形贴在深色模板上"边界极硬，视觉风险未验证。浅色分支至今是推演。
3. **第 2 步「写描述」一个字没做**。三步成片里唯一的护城河，且与版式耦合：五套标题字号是 `fitSize` 自适应，但**没有字数上限**——长标题会被缩到很小，等于把"高级感"自动降级。这个上限必须由版式反算出规则（如 T1/T2 ≤7 字、T3/T5 ≤9 字），写进描述解析层的生成约束。

**下一步推荐（唯一动作）**：造一张白底电商图（现有实景图抠不出，直接用纯白底合成一个商品），跑完整 Node 出片链路一次。这一个动作同时暴露缺口 1 和缺口 2，成本最低、信息量最大。

### 五、【最重大】opentype.js 解析思源系列会丢字形部件

现象：渲染「手作咖啡」时「咖」只剩「加」，左边「口」整块消失。排查过程（都做了，记下来省下次）：
1. 以为是 librsvg（sharp 的 SVG 渲染器）→ 换 resvg（`@resvg/resvg-js` 项目里本就有依赖）→ **同样错**
2. 以为是渲染器 → 用 Chrome headless 渲染同一份 SVG → **同样错**
3. 逐字验证：**单字单独渲染永远正确，多字连排才错**；坐标、子路径数（7 个）、bbox 全部正常
4. 把多个字的轮廓拼进同一个 `d` 属性 → 错；每字一个 `<path>` + resvg → 对；每字一个 path + Chrome → 仍错
5. 换解析库：`fontkit` 同一字**完整正确** → 定案是 opentype.js 2.0 对 3 万字形大字体的合体字解析缺陷

**两条修正都写进 type.mjs 了**：
- 解析库 opentype.js → **fontkit**（`fontkit.openSync` / `font.layout` / `glyph.path.scale().translate().toSVG()`）
- **每个字必须输出独立 `<path>`**，绝不拼成一个 d

**fontkit 的坐标是 y 轴向上**，SVG 是 y 轴向下，必须 `path.scale(s, -s)`，否则整行字上下颠倒（踩过）。

## 18:36 每镜字数：定案自由分配（用户定，我同意但要加一条硬下界）

**用户理由**：自由分配能表达 LLM 意图。这个理由成立——给固定字数区间（如 8–40 字）会让模型为了填满注水、为了压缩砍掉好句子，是真实存在的 LLM 行为。

**但必须加一条硬下界：有台词的镜 ≥ 10 字（约 2.2s）。**
理由不是节奏，是**功能失效**：图片成片的唯一价值是"看清商品"，一镜只念 4 个字（0.9s）观众来不及看清图里是什么就切走了。低于 2.2s 的镜等于白给一张图。

**不设上界**。设上界就要砍台词，砍台词等于程序做创意，违背"引擎不做创意"的分层。长镜有整帧推近撑着，不会闷。

**软建议放 prompt，硬校验放代码**：prompt 里写"单镜建议 2.5–8s、首镜与末镜各 3–5s"，代码只校验 10 字下界。空镜（`line:""`）不受下界约束（故意的纯音乐镜），但空镜总时长 ≤ 全片 20%。

**`target_total_sec` 语义随之定死**：不是承诺，是"这个故事值得讲这么久"的语气密度目标。实际全片时长 = Σ TTS 实测，漂 ±15% 正常，程序不纠正。平台不关心精确到秒。

**顺带印证上一轮**：自由分配会让每镜时长方差变大（2.5s 到 8s），所以整帧推近必须"固定速度"（每秒 0.35%）而不是固定幅度——短镜推得少长镜推得多，反而自然。

## 18:38 推翻 10 字下界：引擎对台词零干预（用户定案）

**用户方案**：不固定台词数；时长完全以 TTS 实测为准；TTS 念的就是 LLM 写的原文。

**我必须承认上一条错了**：10 字下界要落地只有两条路——打回重试（违反"只调一次 LLM"这条自己定的铁律），或在程序里补字改字（程序做创意，违反分层）。两条都不通，所以下界本身站不住。用户的方案更自洽。

**由此推出两个字段的处置（这是这轮真正的收获）**：
1. **`shots[].duration` 删除**。它唯一用途是"我想这镜长一点"，但落地手段就是写长台词，而写长台词本身直接生效 —— 中间层多余。

## 18:47 执行层：视觉随机方案的四条对账（用户提，三条成立两条要改）

**用户方案**：①版式+配对随机一种、全片不变（"版面天然适配各种比例"）②文字动效 2–3 种 ③运镜 2–3 种 ④转场 2–3 种 ⑤结尾按入口随机一种。

**第②条可行，但只能"整层变换"**：淡入（`fade=alpha=1`）/ 上滑左滑（overlay y/x 带 t 表达式）/ 擦除（crop 宽度随 t）。这三种都是**静态 PNG + 滤镜表达式，成本≈0**。做不到的是逐字入场、字距展开、缩放——那是逐帧重排文字，最贵。

**第③条方向要改：图片成片做不了"推近"，只能"平移"。** crop 窗口固定 1080×1920、只在 1112×1976 里平移（x∈[0,32], y∈[0,56]），这物理上就是摇移不是推拉。现有 `MOTION_CYCLE` 6 档里 `0_push_in`/`1_pull_out`/`5_breathing` 三档都要逐帧 scale（8s 素材 +7s），`2_diagonal`/`3_rise_up`/`4_sweep` 三档 crop 可做。要推近只能用**分段伪推近**（生成 5 张不同缩放级别静帧再 concat，段内静止、每段差 2–4px 肉眼不可见），可行但复杂度明显上升，第一版建议不做。

**第④条要剔掉溶解**：`TRANSITION_CYCLE` 里两个 `dissolve` 不能用——两镜标题交叉淡化 = 两套字叠成糊字。可用硬切 / 黑场过渡 / 擦除。

**第⑤条成立**：`ENDING_POOLS` 已按 `sell`/`local`/`personal` 分池。待定形态：独立一镜（需额外无商品背景 + 多一镜 TTS）vs 末镜叠加（推荐，零额外素材）。

**成本**：三者叠加约 10–14s/片（crop 平移 +3.3s、转场少量），不再是全静帧的 6.6s。

**一条独立判断**：片内混 2–3 种不同方向的运动，风险是"相机在乱晃"（像 PPT 切换动画）。建议**片内只取同族**（纵向族：缓升/下沉；横向族：横掠/对角），跨订单才换族。

## 18:54 结尾定案：统一淡黑到黑屏，CTA 在纯黑上出现（用户定）

**这个方案优于我上一条的「叠在末镜」**：末镜条带里已经有标题/说明/编号，再叠 CTA 必然抢位；独立黑屏上只有 CTA，排版完全自由。

**关键发现：4 种骨架本来就自带黑罩。** `packages/cover-kit/endingCta.js` 每个 `renderSvg` 第一件事就是画 `<rect fill="rgba(10,10,14,0.68)"/>` 全屏曜黑底罩（设计意图是叠在商品图上压暗）。用户要的「淡黑到黑屏」= **把 0.68 改成 1.0**，不需要新写骨架。

**转场用 `xfade=transition=fadeblack`，不是 `fade`**：
- `fade` = 直接交叉叠化 → 末镜版式文字与 CTA 文字叠影
- `fadeblack` = 先淡到黑再从黑淡入 → 零叠影，且正好就是「淡黑到黑屏」这个动作

**尾部结构**：末镜 TTS 结束 → `fadeblack` 0.6s → CTA 静止 1.8s，合计 **+2.4s 固定尾巴**，不计入 `target_total_sec` 预算（程序加的）。

**三个必须处理的细节**：
1. **`bgm_on=false` 时 CTA 段完全静音**，1.8s 纯文字像卡住。需从 `materials/audio` 的 `outro_sfx`（9 首）取一个极轻音效。
2. **`vertical_pillar`（中心竖柱）只能配书法类配对**——竖排配思源黑体会变成菜单排版（同版式×配对的既有判断）。另 3 种横排骨架（hairline / ghost_box / pure_typo）任意配对都能撑。CTA 骨架也要进白名单逻辑。
3. **CTA 尺寸是"全屏尺度"**（中文 52px / 英文 32px / 居中 cy=0.5h），不适用于条带，这也反证了独立黑屏是对的。

**必须先修的**：`endingCta.js` 4 种骨架的 `font-family` 全是 `'PingFang SC'` / `'Inter'` 系统栈，而 sharp 渲染 SVG 不认 font-family（本机实测 21 个家族名逐像素相同，全 fallback）——**这 15 款结尾现在渲染出来根本不是设计的样子**。要跟版式层一起走 fontkit 转路径。

**撤回上一轮的一个担心**：CTA 文案不是用全角空格拉字距，`endingCta.js` 里是 `letter-spacing = ZH_FS * 0.22`，真实实现正确。V4 资产表 desc 里看到的「甄 选 呈 现」只是展示写法。

## 18:56 执行层复述 + 八个漏洞（自查）

**复述链路**：固定洞位 A（全片 1080×1440@240）→ 版式+配对全片一种 → 文字映射（title←sub_theme / label←side_typo.text / idx←i-of-N / note←subtitle / site←品牌）→ 每镜 TTS 得时长 → 合成底图 → crop 运镜 → 文字动效 → cut/slide 拼接 → fadeblack 0.6s → CTA 1.8s → BGM 闪避淡出 → 编码。

**八个漏洞，四个是硬伤**：

1. **空镜（`line:""`）没有 TTS，时长无来源。** 现在无任何默认值。需定：空镜固定 2.5s，或用相邻镜实测均值；且空镜总时长仍受「≤全片 20%」约束（原为软建议，落地必须硬校验，否则全片可能全是空镜）。

2. **文字不能烧进静帧——与文字动效直接矛盾（硬伤，改架构）。** 若文字烧在静帧里，运镜会带着文字一起 crop，文字动效就无处可加。必须拆两层：底图（背景+商品）+ 文字透明 PNG。**进一步建议：文字层不参与运镜、位置全片固定**，只做入场动效。三条理由：①overlay 位置只支持整数像素，32px/150 帧 = 每帧 0.2px，取整后每 5 帧跳 1px，缓慢运镜下可见抖动；②文字绝对稳定可读性最好；③文字不动就解锁了更大的运镜幅度——原来 36px 上限是"文字不撞条带边"算出来的，现在只受"不裁到商品"约束（洞区两侧各 130px 墙），可以做到 4–5%。

3. **`pause_after` 落点未定。** 前置（先静 0.4s 再开口）还是后置（说完停 0.4s）？期间运镜是否继续（应该继续，镜头不能停）？建议后置，因为后置停顿是"留白"，前置是"卡顿"。

4. **V4 版式里还留着调试文字（硬伤）。** `lyT('SLOT '+slot.key+' · '+slot.h, ...)` 在 T2 右下角，生产会直接印出「SLOT A · 1440」。必须删。同类：T2 的 `lyT('01',...)` 是写死编号，要改成程序生成的 `i/N`；T3 的 `NO. ${c.idx}` 是设计不是调试，保留但要喂真编号。

5. **`side_typo` 为空时 T1/T5 顶部 label 位缺一块。** 版式几何按"有 label"设计（短线上方 y=76），缺了会显得顶部空。需定：无 label 时隐藏该元素并上移标题，还是用中文小标顶替。

6. **上传图数与 shots 数不一致无兜底（硬伤）。** 用户传 9 张、模型只写 5 镜 → 4 张图不出现 = 直接投诉。这是产品承诺问题，不是文案问题。必须校验并补齐：缺少的镜按上传顺序追加，文案取通用兜底或空镜。

## ⑥ 落地：side_typo 改为每镜必填（用户决策「让 LLM 一次出全」）

## 真跑出来的两个 bug（都被实测抓到，不是推演）

**① 文字鬼影被 eof_action 冻结**
24.9s 全黑画面上还能看见右上角「/ 06」。原因：淡出结束点压在素材末尾，3.9s@30fps 末帧落在 3.867，alpha 只走到 91%，`overlay eof_action=pass` 把这帧冻住保留到片尾。**版面坐标全片固定，残影会跟下一镜文字精确叠在同一位置**，观感只是"字有点脏"，极易漏掉。修法：淡出结束点提前两帧（`outEnd = dur - enterDelay - 2/fps`）。新增单测守这条，并且正则必须带 `:alpha=1`——否则会把「变黑」那层的 `fade=t=out:color=black` 也算进来，误判成文字淡出。

**② 黑透瞬间就浮字，"然后"等于没有**
原来 CTA 淡入起点 = totalSec，与 fadeblack 结束点重合，全黑停留 0 秒。加 `endHoldSec: 0.35`：淡黑 0.6 → 纯黑停 0.35 → CTA 淡入 0.85 → 全亮 2.35。尾巴 3.2→3.55s。实测亮度：24.9s 最亮 6 / 25.2s 纯 0 / 25.5s 49 / 27.9s 255。
顺带修：CTA 输入素材长度从 `ctaSec` 改成 `tailSec`——否则提前 eof，片尾多出一段静止定格。

## 21:50 · 字幕层上线 + 共享层死代码清理

### 字幕为什么"分两套"（用户追问定案）

字幕拆成两件事，只有前一件该共享：

| 层 | 内容 | 落点 |
|---|---|---|
| 文本计划 | 断句、行尾标点、分屏、时间轴、像素宽度 | `packages/subtitle-kit/plan.js`（全平台唯一） |
| 渲染 | 字怎么画上去 | 各引擎自己实现 |

渲染不能合并，因为渲染器物理不同：旧五链路是 **ffmpeg drawtext（freetype 逐帧）**，处理用户上传的任意分辨率视频，
字幕靠描边/阴影自适应任何底色；V4 是 **resvg + fontkit**，画布固定 1080×1920，字幕必须跟版面文字同一套字形度量，
还要圆角胶囊底衬（drawtext 的 box 只能直角、只能贴字）。
**要合并只有两条路，都是倒退**：都改 SVG → 五条链路重算画布/时间轴/输入索引 + 五套 drawtext 动效重写，生产在跑风险高；
都改 drawtext → 图片成片质感立刻掉。**真要收敛，方向是统一到 SVG，等旧链路整体迁到 V4 合成器。**

### 新增

- `packages/subtitle-kit/plan.js`（122 行）：`splitSubtitleCards` / `layoutSubtitleTiming` / `planSubtitles` /
  `charWidth` / `measureText`。断句调共享包已有的 `wrapCJK`，**不另写一套规则**。
- `modules/visual_engine_v4/subtitle.js`（只留渲染，80 行）：`SUBTITLE_STYLE`（字体/行高/胶囊底衬）、
  `SUBTITLE_PLAN`（透给 plan.js 的文本参数）、`buildSubtitleCardSvg`。
- `imageFilm.js`：`planImageFilm` 输出 `subtitleCards`；滤镜图里字幕 overlay 用 `enable='between(t,st,en)'` 控显隐
  （不用 tpad 位移，位移方案一旦 eof 会靠 eof_action 冻结最后一帧，字幕赖着不走）。

## 22:15 · 共享层按"消费者数"归位（判据定稿）

### 判据（本轮定，往后照此办）

一个模块进 `packages/` 当且仅当属于两类之一：
1. **能力**：有 **≥2 个互不统属的调用方**。只有一个消费者的"通用工具"本质是私有实现。
2. **口径**：规定"必须一致"的规则/参数，**即使只有 1 个消费者也要独占一份**（第二个消费者出现时必须守同一条线，不能有第二份副本）。

不该进的两类：**业务逻辑**（只服务一条链路的判断，留链路旁）、**数据表**（只给某脚本做镜像的原料，跟着脚本走）。
②③ 的分界线：**换一条链路，这条规则还成立吗** —— 断句规则换成切片链路照样成立（②）；排镜规则只在导演链路成立（③）。
