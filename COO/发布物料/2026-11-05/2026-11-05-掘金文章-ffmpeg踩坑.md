## 正文

我是刘强，一个独立开发者，最近一年多在做一件事：让商家把商品照片丢进去，自动出一条能发布的带货视频。管线里最重的脏活——把分镜素材、配音、字幕、BGM 合成成片——全部压在 ffmpeg 上，服务端每天要跑批量渲染任务。

网上讲 ffmpeg 播放器、转封装的教程很多，但讲"无人值守批量生产"的几乎为零。这七条坑全是我一行一行试出来的，写给你，希望你少熬几个夜。

### 坑 1：转场滤镜在某些 Windows 构建上直接崩溃

我用的是 gyan.dev 的 Windows 构建，`xfade` 挂 `slideup`（向上滑动）转场时进程直接崩，退出码 `0xC0000005`（内存访问违例），没有日志没有栈。换成 `slidedown` 一切正常——同版本构建、同参数，只有这一个方向会崩。

教训：**ffmpeg 的滤镜组合问题要先怀疑"这个构建"而不是自己的代码**。遇到玄学崩溃，第一动作是换一个官方构建（BtbN / gyan）交叉验证，第二动作是把滤镜挨个二分。

### 坑 2：商品图不要用 dissolve 转场

dissolve（溶解）转场在人物、风景素材上很美，但用在商品图上就是灾难：两张图叠化时商品主体互相透底，看起来像"双重曝光的糊图"，观众只会觉得"这图怎么是花的"。商品图切换老老实实用硬切或者滑动类转场。

**转场选择不是美学问题，是素材类型问题。**

### 坑 3：淡出必须比素材提前至少 1 帧结束

`fade=t=out:st=...:d=...` 的结束时间点如果正好等于视频流末尾，最后会残 1~2 帧未淡出的画面——成片结尾闪一下。所有淡出时间轴整体前移至少 1 帧，按 24fps 算就是 40ms 出头。这种问题单看代码永远发现不了，只有盯着成片最后一秒看才看得见。

### 坑 4：Ken Burns 用 zoompan 会抖，用纯平移

想让商品图有"运镜感"，第一反应是 `zoompan`。但 zoompan 的缩放插值在整数像素上跳变，缓慢推近时画面会周期性抖动。商品图场景里我全部改用纯平移（cropping window 匀速移动）——放大其实不是必须的，**平移已经足够营造"动起来"的感觉，而且零抖动**。

### 坑 5：filter_complex 拼接的占位符替换，小心尾逗号

Node.js 里动态拼 `filter_complex` 时，我习惯用 `[bgm]` 这类占位符标记 BGM 输入，最后做字符串替换注入实际的滤镜链。坑在于：替换后如果留了尾逗号，整条 filter 链解析失败，而 ffmpeg 报错只会说 "Invalid argument"——不会告诉你错在哪一段。**动态拼 filter 链的每一步替换后都做一次括号/逗号配平检查**，能省掉大量玄学排错时间。

### 坑 6：编码参数别追"最好的"，要定版

veryfast / crf 23 / 24fps——这组参数我测试后就锁死了。服务器批量渲染的瓶颈从来不是单条视频的压缩率，而是吞吐量：并发池拉太高，CPU 打满，每个任务都变慢，还容易把内存打爆。我的定案是**并发池恒定 2**，单任务时自然退化成串行——上限不是开销，是保护。参数一旦定版就不要每天调，每次"优化"都是一次回归风险。

### 坑 7：`JSON.stringify(error)` 会丢掉 message

最后一条是 Node.js 侧的：渲染失败时直接 `JSON.stringify(error)`，日志里只会得到 `{}`——因为 `Error` 的 message 和 stack 是不可枚举属性。批量任务失败排查全靠日志，日志丢了就等于瞎了。我的做法是统一落 `{ name, code, status, message }` 四个字段的结构化错误对象。这个坑不值钱，但它坑你的时候你最疼。

### 写在最后

ffmpeg 这类工具的"上手教程"满地都是，但"生产环境教程"凤毛麟角——因为每个坑都要用真实的渲染量才能喂出来。以上七条全部来自我自己的 AI 视频生产管线（工具叫简兮，感兴趣的可以搜 [jansee.cn](https://jansee.cn)），没有一条是抄来的。

你在做类似的批量合成管线吗？评论区聊聊，转场崩溃这种玄学问题，多个样本总是好的。
