# 生图优先路线评估（Image-First）

> 起因：生视频模型无法可靠命中屏槽坐标，且成本/耗时/不可控性都高。
> 提案：改为「AI 生一张精美的场景图，屏里由程序贴用户商品图」。
> 本文是实测结论 + 三个必须解决的技术点 + 与现有 v4 引擎的关系。

---

## 一、实测数据

同一台机器，输出规格统一：**1080×1920 · 30fps · 8s · 240 帧 · H.264 crf18 medium**。
脚本：`storage/tmp/bench/bench2.mjs`（`node storage/tmp/bench/bench2.mjs` 可复现）。

| 环节 | 墙钟 | 峰值内存 | 产物 |
|---|---|---|---|
| A0 纯转码背景视频（基线） | 34.5s | 629MB | — |
| **A 视频背景 + 逐帧 overlay（现方案）** | **27–40s** | **678MB** | 0.18MB |
| **B 图片背景 + 一次合成 + 推近出片** | **8.2s** | **590MB** | 1.16MB |
| C 只出静态图（sharp，不出视频）**【仅对照组，不是产品形态】** | 0.36s | ~60MB | 256KB |

> **「产物」列不可当作优劣对比**：A 和 B 出的都是视频，体积差 6 倍不来自载体，来自画面信息量。
> A 用的测试背景是程序合成的近乎静止场景（一条反射光带缓慢扫过），crf18 只给它 186kbps；
> B 的画面每 2.8s 换一张商品图 + 整幅推近，编码器给了 1456kbps。
> **成片体积最终由编码参数决定，不由背景是图还是视频决定**——锁死 12Mbps，两者都是 12MB 上下。
> 顺带：186kbps 远低于抖音成片要求（≥12Mbps），A 那个 0.18MB 是缺陷不是优势。
> 也说明本次 A 的测试素材偏"干净"（真实 AI 生成的视频带噪点和运动，重编码后码率会高得多），
> A 的实际成本只会比这里更高，不会更低——不影响"B 更快"的结论，但不能用产物体积做论据。

> A 两次测量 27s / 40s，机器噪声约 ±30%，取量级看：**B 比 A 快 3.5–5 倍**。
>
> **C 的存在只为一件草：分离出「出 8s 视频」这件事本身的刚性成本。**
> 简兮是出视频的平台，C 不上线、不作为产品形态。它唯一可能的用处是给封面出一张静帧（见结论 2 末尾）。

### 结论 1：时间省 70%，吞吐提升 3.4 倍

- A 路线：27s/单 → 8 核并行约 3.4s/单 → 单机理论 **≈1050 单/小时**
- B 路线：8.2s/单 → 8 核并行约 1.0s/单 → 单机理论 **≈3600 单/小时**
- 两条路线的终点都是 8s 视频，没有第三条「只出图」的产品路线

### 结论 2：内存只降 13%，这部分"友好"是假的

629MB → 590MB。**ffmpeg 的内存峰值大头是 x264 编码器的帧缓冲队列，不是解码输入。**
只要最终还是要出 8s 视频，这块内存就躲不掉。

编码刚性成本单独拆出来看：A0 纯转码不带商品就已经 34.5s / 629MB，说明"出 8s 1080p 视频"这件事本身的底价就在这。**这条底价 A 和 B 都要付，改生图也绕不过去。**

对照组 C（0.36s / 60MB）说明的是：一旦不编码视频，成本立刻掉两个数量级。它唯一的现实用途是**封面**——抖音首帧即封面，`packages/cover-kit` 需要一张精修静帧，那个场景用 C 是合适的，且和出片流程共用同一次合成。

### 结论 3：背景素材体积差 21 倍（注意：是素材，不是成片）

- 背景视频 **素材** 5.5MB / 8s
- 合成后的场景图 **素材** 256KB

成片体积另算，由编码码率决定（见上）。这里说的是**素材库和分发成本**：场景图可以长期存、反复用，视频素材用一次就废。

## 二、一个必须纠正的理解

> "生成精美的图，里面有一个屏，屏里放用户图片"

**不能让 AI 把用户图片画进屏里。**

只要商品图经过生图/生视频模型，就会出现：
- logo 变形、字母错乱（扩散模型对文字是硬伤）
- 商品颜色/材质被重绘，与实物不符
- 细节被"脑补"，退货率会上升

**正确分工**：

```
AI 只负责「空屏的场景」     → 屏可以是任何形状、角度、透视
程序负责「把用户图放进屏」   → 像素级精确，商品 100% 保真
```

这也正好延续上一轮定下的铁律：**几何由程序保证，不由模型保证。**
模型把屏画到哪、画多大、画多斜，都不重要——程序测得出来就能贴准。

## 三、生图路线真正的商业价值：场景变成资产

这是它比"省 CPU"重要得多的理由。

| | 生视频 | 生图 |
|---|---|---|
| 单次生成成本 | 按秒计费，8s 约几元 | 按张计费，单张几毛 |
| 一次生成几次可用 | 1 次，废了就废了 | 出 4 张选 1 张，可人眼挑 |
| 能否复用 | **不能**，每单都要重生成 | **能**，一张场景跑无限商品 |
| 边际成本（第 1000 单） | 仍是全额生成费 | **≈0**，只剩 0.36s 合成 |

**20 张场景图 = 20 个模板，可以跑 1 万个商品。**
**20 段视频 = 20 个一次性素材，跑 20 个商品就没了。**

这才是"改生图"最大的收益，远超 CPU 那 70%。

## 四、三个必须解决的技术点

### 1. 屏区定位（新增工作量，但只做一次）

生图出来后，需要知道屏在画面里的精确位置。三条路：
- **人工标一次**：一张图点四个角，10 秒。20 张模板也就几分钟。**首选，最稳。**
- 程序自动检测：亮度/梯度找亮矩形，复杂度高、易被树影橱窗污染（已在此前视频素材上踩过坑）。
- 生图时要求"屏为纯色/高亮"，再用色块检测。可行但要约束提示词。

定位结果存进模板元数据（沿用 `screen-geometry-spec.md` 的 JSON 结构），商品进来直接读。

### 2. 透视贴合

屏如果不是正对镜头，四角会构成梯形。用 ffmpeg `perspective` 滤镜按四角做单应变换，把矩形商品图映射上去：

```
perspective=x0:y0:x1:y1:x2:y2:x3:y3:sense=source
```

配合 `v4` 引擎现有的 overlay 逻辑即可。**风险中等**：反走样和边缘会出现 1–2px 锯齿，需要 2× 超采样后再缩回。

### 3. 画面"死"的问题（最大的观感风险）

静态图 + 推拉，观众一眼看出是"图片在放大"，完播率会掉。

三个解法，按性价比排序：
- **屏内内容动起来**（首选）：屏里是用户商品图，做轮播/滑动/淡入。这是画面里唯一"合理该动"的东西，动得自然，而且**正好是 v4 引擎已有的能力**。
- **景深微视差**：AI 图 + 深度图 → 2.5D 分层。效果最好，但要引入深度估计模型，成本上一个台阶。
- **氛围层**：光斑扫过、屏幕反射呼吸、极缓慢推近（0.07 倍率，实测 8s 不晕）。

**建议组合**：屏内轮播（主）+ 极缓慢推近（辅）+ 一次性光斑扫过（点缀）。

## 五、与现有 v4 引擎的关系

`modules/visual_engine_v4` 的定位就是「**固定背景 + 商品窗口轮播**」，`renderer.js` 里已有 `buildProductWindowFilterGraph` 和 `buildFixedImageFilterGraph`，输入就是一张背景图 + 多张商品图 + 归一化窗口坐标。

**也就是说，这条路线在项目里已经有一半了**，缺的是：
1. 场景图从"程序画的纯色屏"换成"AI 生的真实场景（带透视）"
2. 增加屏四角定位 → perspective 校正这一段
3. `window` 从归一化百分比改为读模板 JSON 的绝对像素坐标

不需要从零造，是给 v4 换引擎盖。

---

## 六、建议的落地顺序

1. **先锁死"屏必须是矩形平屏"**：提示词里明确要求屏正对镜头、无透视畸变。这样能跳过 perspective，直接 overlay。**第一批先不做透视，把链路跑通。**
2. 生 3–5 张场景图，人工标四角，存模板 JSON。
3. 用 v4 引擎跑通「场景图 + 3 张商品图 + 轮播 + 推近」出 8s 片。
4. 验收：`node scripts/check-material.mjs` 对成片跑一遍（脚本目前只吃视频，需支持图片输入）。
5. 透视版本作为 v2 迭代，等第一批跑通再上。
