## 一、总体结论

**语法健康、佣金规则正确、持久化设计扎实；但资金与鉴权层面存在多处致命漏洞，当前版本不能直接对外收费。**

风险统计：

| 级别 | 数量 | 含义 |
| :-- | :-- | :-- |
| P0（致命，立即修） | 4 | 可被直接利用造成资金损失 / 越权 |
| P1（高危，尽快修） | 7 | 资损、越权、稳定性隐患 |
| P2（中危，计划修） | 9 | 加固缺口、可维护性 |
| P3（低危，择机） | 3 | 遗留与整洁度 |

**最要命的一句话**：当前"支付确认"接口不校验支付真实性，积分/金额由客户端自报——任何人可以不付钱拿到任意积分和会员。

## 二、安全（Security）

### P0-1 后台硬编码后门（超管凭证写死在源码）
- **位置**：`apps/web/server/index.mjs:1044-1048`
- **问题**：`requireAdminAuth()` 只要请求头带 `x-admin-key: jansee-admin` 就直接返回 `super_admin` 身份。
- **危害**：任何知道/猜到 `jansee-admin` 的人，可调用全部 `/api/v1/admin/*`——改用户、调积分、退款、审批提现、看佣金、改价格。再叠加下面 CORS 通配，任意网页都能跨站调用。
- **改法**：删除该分支，后台只认 `adminToken`（已用 `crypto.randomBytes(16)`，够强）；如需运维密钥，走环境变量 + 常数时间比较。

### P0-2 用户越权 / IDOR（身份来自客户端自报）
- **位置**：`apps/web/server/index.mjs:402-408`（`pickUid`），被资料、订单、合伙人、提现等大量接口使用
- **问题**：`pickUid` 依次信任 `x-user-id` 头 → `payload.userId` → `query.userId`，**完全不校验会话**。
- **危害**：换个 `userId` 就能读/写他人账户数据（资料、手机号、积分、订单、佣金）。
- **改法**：用户态接口统一从 `verifySession(extractSessionToken(req))` 取 `userId`，禁止客户端传 uid；`pickUid` 仅在开发态保留。

### P1-1 会话 Token 弱随机
- **位置**：`apps/web/server/auth.mjs:24`
- **问题**：`sess_${Date.now()}_${Math.random().toString(36)...}`，`Math.random` 非密码学安全。
- **改法**：`crypto.randomBytes(32).toString('hex')`。

### P1-2 限频可绕过
- **位置**：`apps/web/server/rateLimit.mjs:29-36`
- **问题**：`clientIp` 盲信 `X-Forwarded-For` 首值。直连场景攻击者每次伪造不同 XFF 即得全新计数桶，限频形同虚设。
- **改法**：仅当配置了受信反代（如 `TRUST_PROXY=1`）才读 XFF，否则用 `req.socket.remoteAddress`。

### P1-3 默认弱口令 + 明文存密码
- **位置**：`apps/web/server/adminStore.mjs:24`（默认 `admin123`）、`:57`（`password: cleanPwd` 明文）
- **改法**：强制要求环境变量设置强密码（未设置则拒绝启动）；密码用 bcrypt/scrypt 哈希存储。

### P2-1 CORS 全通配
- **位置**：`apps/web/server/index.mjs:160-165`
- **问题**：所有响应（含后台）`Access-Control-Allow-Origin: *` + `Allow-Headers: ... *`。
- **改法**：Origin 白名单；后台接口禁止 `*`。

### P2-2 静态分发缺目录包含校验
- **位置**：`apps/web/server/index.mjs:1594`（`/admin`）、`:1609`（`/storage/outputs`）
- **说明**：这两处只 `path.join`，无 `startsWith(基目录)` 校验（materials 分支有）。**实测** `/admin/../../.env` 被 Node URL 规范化挡住，返回的是 index.html 兜底（713KB≈index.html，非 .env 9.6KB），**未构成可利用穿越**。
- **改法**：补 `resolve 后 startsWith 基目录` 的纵深校验，不依赖框架行为。

### P2-3 敏感词/广告法合规覆盖
- **位置**：`apps/web/server/sensitive.mjs`
- **说明**：有过滤实现，但需确认所有出片文案/发布五件套路径都过 `sensitive`。建议加一条"绕过即报错"的回归用例。

## 三、支付（Payment）—— 最严重区域

### P0-3 支付确认不校验真实性（凭空领积分）
- **位置**：`apps/web/server/index.mjs:1396-1454`（`POST /api/v1/order/pay-confirm`）
- **问题**：拿到 `orderId` 就 `markPaid()` → 立即 `chargeCredits` 加积分 → 开会员 → `grantCommission` 发佣。**无验签、无向支付通道查单、无登录态、无订单归属校验。**
- **危害**：任何人 POST 一个 orderId 即可把订单标记为已支付并领取全部权益，零成本。
- **改法**：该接口仅供收银台轮询展示；真正的入账只允许由支付通道异步通知（带签名验签 + 金额比对 + 幂等）触发，且校验 `order.userId === 当前登录用户`。

### P0-4 下单金额/积分由客户端决定
- **位置**：`apps/web/server/index.mjs:1379-1389`
- **问题**：`createOrder({ amount: payload.amount, points: payload.points, ... })`，服务端不按后台定价重算。
- **危害**：可下 `amount:0.01, points:1000000` 的单，实付 1 分钱换百万积分。
- **改法**：只接受 `pkg/tierId`，金额与积分数一律由服务端价目表（`siteConfig` 定价）反查，拒绝客户端传入的 amount/points。

### P0-4b 客户端可自设积分余额
- **位置**：`apps/web/server/creation.mjs:195-196`
- **问题**：当账户余额为 0 时，直接 `store.accounts.set(uid, payload.user.points)`——用客户端传来的积分初始化账户。
- **危害**：新用户或已消费到 0 的用户，发 `user:{points:999999}` 即得任意积分。
- **改法**：删除该初始化逻辑，账户只由服务端 `chargeCredits/grantFreeCredits` 产生。

### P1-4 未登录可免费出片
- **位置**：`apps/web/server/creation.mjs:229-230`
- **问题**：无 `effectiveUserId` 时直接 `return { ok:true, userId:null, remainingCredits:2850 }`，不扣费照常出片。
- **改法**：生产环境要求必须登录；无身份直接 401。

### P1-5 出片失败退款失效（用户丢积分）
- **位置**：`apps/web/server/creation.mjs:1208`
- **问题**：调用 `store.addCredits(...)`，但 `creditStore` **没有 `addCredits` 方法**（`index.mjs:1667` 已改为 `refundCredits`，这里漏改）。异常被内层 catch 吞掉，积分退不回来。
- **改法**：改为 `store.refundCredits({ userId, amount, reason, taskId })`；补一条"失败必退款"回归用例。

### P1-6 退款把免费积分洗成付费积分
- **位置**：`apps/web/server/creditStore.mjs`（`refundCredits`，约 399-423 行）
- **问题**：扣费优先扣 `free`，但 `refundCredits` 一律补回 `paid`。free 是不可提现的赠送积分，paid 是可退款/可提现的真金。
- **危害**：反复"出片→失败→退款"可把赠送积分洗成付费积分，进而套现/套退款。
- **改法**：消费交易里结构化记录 `deductFromFree/deductFromPaid`，退款按原拆分分别退回 free/paid。

### P2-3 退款通道与佣金账期时序
- **说明**：`refundOrder` 只允许 72 小时内退款，佣金 7 天结算，普通路径下不会"已结算后被退"。但 `markRefunded`（通道异步退款通知）可晚于 72h 发生，仍可能产生已结算佣金无法追回（仅打 `clawback` 标记不扣余额）。建议对已结算回滚加人工对账流程。

### 做得对的部分（要保留）
- `payStore.markPaid/refundOrder` 幂等；订单状态机清晰（pending/paid/refunding/refunded/expired/revoked 分离资金与权益）。
- `dataStore.writeJsonAtomic`：写临时文件 → fsync → rename，崩溃不留半截 JSON。

## 四、返佣（Commission）—— 质量最高的模块

**核心规则全部正确，单测 100% PASS**：
- 仅会员充值（member/renew）计佣，加油包（points/boost）硬性 0 分润；
- 一级 15%、二级 5%、单笔总返佣硬锁 ≤20%；
- 自买自返拦截（`inviter.id !== payerId`、`grand.id !== payerId`）；
- 7 天账期、退款冲正（pending→cancelled，settled→仅打 clawback 标记不静默扣余额）；
- 提现 6 重门禁（门槛/单笔/单日额/单日次数/可提现余额/密码二次验证）+ requestId 幂等；
- 已废弃的 `submitDirectWithdraw` 永久停用，堵住无限提现。

### P2-4 可提现余额未扣 clawback
- **位置**：`apps/web/server/partnerStore.mjs:240`
- **问题**：`withdrawable = settled − withdrawn`，未扣减已被 `clawback` 标记的已结算佣金。
- **危害**：极端时序下（已结算后被退款的订单），用户仍可提走该笔佣金。
- **改法**：`withdrawable` 计算时排除 `clawback` 金额。

## 五、稳定性（Stability）

### P1-7 无进程守护
- **说明**：网关单进程裸跑，无 pm2/systemd/cluster/自动重启，异常退出即全站不可用（本会话已多次掉线）。
- **改法**：生产用 pm2/systemd 托管，至少 2 实例 + 优雅重启。

### P1-8 致命异常被吞、进程不停机
- **位置**：`apps/web/server/index.mjs:13-18`
- **问题**：`uncaughtException` / `unhandledRejection` 只 `console.error`，不退进程。进程可能在半损坏状态继续运行（如监听失败仍在跑却无服务）。
- **改法**：记录后 `process.exit(1)`，交给守护进程重启。

### 关于本会话"6 分钟掉线 / exit 127"
- **结论（诚实说明）**：经排查，更符合**后台任务被运行环境回收**（exit 127、约 6 分钟一次、中间正常服务），而非代码崩溃。但这恰恰暴露"无守护"的真实风险。

### P2-5 部分定时器未 unref
- **位置**：`apps/web/server/metrics.mjs:169`、`apps/web/server/userStore.mjs:575`
- **说明**：生产无害，但会让测试进程不退出。

## 顺手发现（本次修定价时暴露，不在原审计清单内）

**会员购买根本没有产生佣金。** 前端传 `orderType='membership'`，而 `commissionPlan.commissionRates()`
的键是 `member/renew/points/boost`，`COMMISSION_RATES['membership']` 取到 `undefined`，
`grantCommission` 直接 `return []`。等于合伙人推广会员一直白干。
本次定价改造把 kind 收敛为服务端裁定的 `member`，该链路才真正打通 ——
**注意这意味着今后会员订单会开始产生 15%/5% 佣金支出，属于修复既有 bug，而非新增功能。**

## 明确未修（附原因与正确路径）

1. **IDOR：`pickUid` 信任客户端 `x-user-id`**（`index.mjs`）。
   正确修法是「用户态接口一律从 session 取 userId」，但当前前端所有请求只带 `x-user-id`、
   并不带 sessionToken。改后端会让全部用户态接口 401、前端整体瘫痪；改前端涉及数十处调用点。
   这是一次独立重构（建议：前端统一注入 `Authorization: Bearer` → 后端 pickUid 只认 session →
   灰度观察一周 → 移除 header 回落）。**不做「有 token 用 token、没 token 用 header」的折中加固**，
   那是假安全，攻击者不带 token 即可绕过。
2. **`billingMode` 单月价未区分**：`pricing.json` 只有 `price`（首月/连续价）与 `strike`（原价文案），
   没有独立的单月价字段。当前一律按 `price` 成交（对用户有利，不会多收）。
   接真实支付前需在 `pricing.json` 与 `DEFAULT_MEMBER_PRICING` 补 `singlePrice` 字段。
3. **CORS 仍为 `Access-Control-Allow-Origin: *`**：删后门后后台接口已需 token，
   `localStorage` 不跨站可读，风险大幅下降；但正式上线前应改为来源白名单。
4. **网关反复掉线**：本次未定位根因（现象为进程约 6 分钟后 exit 0/127 退出，
   非端口占用、非未捕获异常）。属进程守护缺失，建议加 systemd/pm2 或自愈守护。
